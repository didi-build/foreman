- **Status:** decided by Didi on 2026-11-19 (D-427 to D-430, D-432 for where the run executes, and D-433 for its own namespace and keys). The first slice built the cases, their loader and their checks. Slice 2a built the test job's image (`src/agent-images/eval/`, O-155). Slice 2b starts the Job, and adds the results tables, the setting, the schedule and the daily line (O-156, "The wiring" below).
- **Date:** 2026-11-19
- **Related:** D-204, D-206, D-207, D-209, D-249, D-369, D-423, D-425, D-427, D-428, D-429, D-430, D-431, D-432, D-433, O-152, O-154, O-155, O-156, [ADR 0101](./0101-repo-layout-and-tooling.md), [ADR 0106](./0106-agent-execution-environment.md), [ADR 0107](./0107-agent-dispatch-adapters.md), [ADR 0112](./0112-qa-runtime-github-access-and-independence.md), [ADR 0114](./0114-model-evaluation-routing-and-tiers.md) section 7, `spikes/visual-model-test/`

## Context

D-204 approved a weekly evaluation set: about 10 past items, replayed on candidate models, open models on DeepInfra Flex only, a hard cap of 10 USD a week held as a setting, and Claude once a month as a baseline inside the cap. ADR 0114 section 7 calls it "an optional evaluation set".

The rehearsal showed why live runs cannot answer which model suits which role:

- Triage split a plan for one small helper into two items, the helper and then its tests (didi-build/rehearsal#9 and #10). Whether another model would have kept it whole can only be seen by giving it the same plan.
- QA passed three tiny helpers (#7, #8 and #9). They were correct, so the passes were right, but a model that passes everything would have done the same. A pass on correct work does not show strictness. Only a defect planted on purpose shows whether QA catches it.
- QA, the Council and Triage moved to DeepSeek V4 Pro on Flex on 2026-11-18 (D-425), and D-209's switch of QA independence to model family waits on a quality check.

Live runs give one answer per item on whatever work comes, so two models never see the same input. A fixed set, given to each model the same way every week and scored the same way, gives that comparison.

## Decision

1. **A separate harness outside the work pipeline (D-427).** Like `spikes/visual-model-test/`, each fixed case goes to each model through the same instructions (the bot files in `contracts/bots/`), the same input builders, the same Messages API frame and loop (`src/agent-images/claude-api/`) and the same answer checks the real runs use, and is scored. It never touches a real repository, never creates a work item and never merges. v1 covers QA's review (`qa:review`), Triage and the Council. The Developer comes later, since judging code needs running it. Rejected: full replays through Foreman on a scratch project.
2. **Twelve cases that mature with Foreman (D-428).** The v1 list is below. Each case is a versioned file that records its source and the date it was added. New cases come from real work: a QA miss found later, Didi or the Council correcting a bot, a new role or task type, the first real project. Each is proposed in a pull request that Didi approves by merging. Once real project work exists, the tiny-helper cases are replaced. A case that every tested model has passed 8 weeks in a row is flagged in the weekly summary as a candidate to replace with a harder one.
3. **The models (D-429).** Each week, all on DeepInfra Flex: `deepseek-ai/DeepSeek-V4-Pro-0813` (today's QA, Council and Triage model, D-425), `deepseek-ai/DeepSeek-V4.1-Flash-1017` (a cheap challenger) and `moonshotai/Kimi-K2.6` (another family, D-209's example). Once a month, Claude as the baseline: Claude Opus 5.5 for the QA cases, Claude Sonnet 5.5 for the Triage and Council cases. Estimated cost: about 0.30 USD a week on DeepInfra, about 2 USD a month on Claude.
4. **Results (D-430).** A results table in Foreman's database (one migration, in the next slice) and a short line in the daily check: which model got which cases right, what it cost, and what changed since last week.

## How it works

### Where the cases and the code live

- **The cases are data in `eval/cases/`**, one folder per case: `case.yaml` and, for QA and Triage, `tree/`, the small repository the run works on. They sit at the root like `contracts/`, outside every folder the TypeScript compiler, Vitest and the build read (`tsconfig.json` and `vitest.config.ts` include `src/`, `test/`, `spikes/` and a few named files, never `eval/`). That matters because the trees hold TypeScript: under `src/` or `test/` a fixture's own tests would run inside Foreman's suite, and its files would be compiled as Foreman code. ESLint, Prettier and secretlint still read the trees, which keeps every fixture file valid, formatted code, as a real pull request's would be.
- **The code is in `src/eval/`**: plain TypeScript with unit tests next to it (ADR 0101). It reads files and YAML, so it cannot be in `src/core/`, which has no file access. It is not a spike: it runs every week from the next slice on. It is not in `flows/`: D-427 keeps it outside the work pipeline.

### A case

`case.yaml` holds the id (also the folder's name), a version, the role and its one task type (`qa:review`, `triage` or `council`), a title, the date added, the source, the input, the expected answer with the reason it is right, and an example of a correct answer. The source is `real` (merged work or a submitted plan), `planted` (a real case with a planted defect) or `written` (written for the set), with a reference and a note on anything shortened or made up.

The loader (`src/eval/cases.ts`) refuses a malformed case with an error that names the case file and the field. It checks exact fields, the role's task type, ids, commits and paths in their forms, and that every file a case names is in its tree. Provenance is checked too:

- A file from merged work is listed with its git blob id at the source commit, and the file in the tree must hash to it, so it is the merged file byte for byte.
- A planted case names the case it is built from and its exact edits. Its tree must be the base's tree with those edits applied and nothing else, and its changed files the base's plus the edited ones.
- No tree holds the case file. QA's tools read only the tree, so the expected answer can never reach the model.

Trees are kept small: the helper, its test, `README.md`, and `package.json` cut to its scripts and the two packages the code needs. Triage's trees hold the code files at the commit the plan was split at, and the gallery files for the page case.

### Inputs, built by the runner's own builders

`src/eval/inputs.ts` builds each case's task file as the runner builds a real run's, and checks it with the runner's own task file check (`taskFileJson`). The instructions come from the role's bot file. Nothing in the harness writes an instruction or a rule of its own.

- **QA:** `taskInput` (`src/core/task-input.ts`) over the work item, the repository, the pull request, the head commit and the pull request's change, as `flows/lib/start-run.ts` calls it, and the evidence ids the run may cite. QA's read-only tools (`src/agent-images/claude-api/files.ts`) read the case's tree. QA's answer schema is the verdict contract the image holds.
- **Triage:** the repo map built from the case's tree at the case's commit by the repo map adapter (`buildRepoMap`, `readCheckout`), checked as the runner checks a map (`checkRepoMap`), then `triageInput` (`src/core/triage.ts`) with the plan, and the bot file's answer schema.
- **The Council:** `escalationInput` (`src/core/council-input.ts`) over the escalation as the runner gathers it, and the bot file's escalation schema. A builder's stop carries exactly the two reasons the runner records: its own reason on the escalation move and the escalation guard's detail with the bot's words. A test checks both against the runner.

Since D-431, QA's input also carries the pull request's change: its changed files and their diff from the merge base to the head commit, as GitHub's compare gives a real run (O-154). The harness computes the change from each case's trees (`src/eval/change.ts`), so no case stores patch text. The base is the repository before the pull request: for a case from merged work, its tree without its changed files, since each of #7 to #9 only added its helper and its test; for a planted case, its base case's. So a case from merged work shows each added file in full, and a planted case shows its base's files as merged with its planted edits, and `qa-truncate-readme-change` also shows `README.md` as a modified file. The merge base the input names is an id made up from the base's files, as the planted cases' head commits are made up. No case file changed, so every case stays at version 1; the set has not run yet.

Since ADR 0119's slice 3a (D-468), QA's and Triage's inputs end with the short summary of the project's records, as a real run's do (`src/core/run-context.ts`). A case holds no project records, so its summary says "No records yet." (`emptyRunContext`). This is a known gap: until a later slice gives cases records of their own, the set does not measure runs with a summary. No case file changed, so each case keeps its version, and a result from before this slice was measured without the section. The Council's cases get no summary, as real Council runs get none.

### The run (the test job, D-432)

The run executes as a Kubernetes Job behind an egress proxy, as the repo map Job and the agent runs do (D-432). The proxy adds each provider's key to each request, so no Foreman code holds a key, and every model call keeps the proxy's request ceiling, its count of 429 answers and its reading of the served tier (D-423). The Job's image is `foreman-eval`, built from `src/agent-images/eval/` (O-155).

For each model and case, the job sends one run through the Messages API loop (`runLoop`) with the image's own frame, which the Messages API image exports for it (`qaReviewFrame`, `structuredFrame`): `systemText` around the bot file's instructions and `fencedInput` around the input, with QA's head commit and evidence ids after it. QA gets its three read-only tools over the case's tree. How each provider takes the answer and a cache key is the role's bot file's `messages_api` for that provider, exactly as a real run gets it: on DeepInfra, which has no structured outputs, the answer comes through the answer tool and the run's id goes as `prompt_cache_key` (O-152); Claude answers through structured outputs. Turn, minute and dollar limits come from the role's bot file. Each case runs once per model per week (`RUNS_PER_CASE`). A repeated run per case, to measure consistency as the vision model test does, can come later if one run proves too noisy.

### Scoring

`src/eval/scoring.ts` scores the run's final text. An answer the runner's own check for its role refuses is `unusable`, whatever it says. A usable answer is `correct` when it meets the case's expectation and `wrong` otherwise. No model judges an answer. Each score also gives a fixed code for its reason (`SCORE_CODES`, for example `wrong_verdict` or `answer_rejected`) and, for a usable answer, a few facts the runner's check has read: QA's verdict and the files its findings name, Triage's item count, the Council's outcome and its two flags. The test job records the code and the facts, never the answer's text.

- **QA:** `parseVerdict` with the case's evidence ids, as the image checks a verdict. Then ADR 0112's citation rule, which the runner is to apply when it records a verdict but does not yet: every finding names a file at the head commit and lines inside it. A pass case wants `pass`. A fail case wants `fail` with at least one finding on a file the case accepts.
- **Triage:** `checkTriageAnswer` against the case's repo map, as the runner checks an answer before it creates anything. Then the items: as many as expected, each expected item matched to its own answer item that covers all its paths (a path or a folder that holds it), each blocked by exactly the items the case names, and needsDidi and hold as expected.
- **The Council:** the escalation schema and `readEscalationAnswer`, as the runner reads an answer. Then where the item goes, by the runner's rule: it stays with the Council only for `resolve` with both flags false. A test checks the harness's rule against the `council_decision_recorded` guard on every combination. A case routed to Didi also names the reasons that count.

### Cost and the weekly cap

Each response is priced from the model catalog entry of the route, at the tier the response reports, or at Standard when it reports none (ADR 0114 section 8), as the loop already prices a run. The plan gives each model its catalog price; an entry without a usable price is refused before any model call (ADR 0114 hard rule 2). The cap of 10 USD a week is a setting. The job starts the week's spend at what earlier runs of the week recorded, which it is told. Before each run, once the spend has reached the cap, it records the run as skipped and never starts it; otherwise it gives the run a dollar limit of the smaller of the bot file's limit and what is left. The loop stops before a request once a run's cost reaches its limit, so a week can pass the cap by at most one request. Claude's monthly baseline counts toward the same cap.

### Results and the daily line

Each run writes one row to the results table: the week, the case id and version, the model, its provider and served tier, the outcome and its detail, the cost, tokens, turns and time. The daily check gets one short line after each weekly run: per model, how many cases were correct, what the week cost, and which cases changed outcome since last week. A case every tested model has passed 8 weeks in a row, at the same version, is named there as a candidate to replace.

### The test job's contract (D-432)

The job reads only its environment, the cases and the bot files its image holds. Every input is checked before any model call; a problem names the setting, the entry and the field, never a value, and stops the job with an error result line.

| Input                                                                          | What it holds                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FOREMAN_RUN_ID`                                                               | The job's id, in a run id's form. Each run's `prompt_cache_key` is `<id>-<n>`, n its place in the job's order.                                                                                                                                                                                                                                                   |
| `FOREMAN_EVAL_PLAN`                                                            | The week's plan: a JSON list of 1 to 8 entries, each `{model, provider, tier, price, roles}`. `price` is the catalog entry in the shape a run gets it (`FOREMAN_MODEL_PRICE`). `roles` are the case roles the entry runs: Claude's baseline is Opus 5.5 for `qa` and Sonnet 5.5 for `triage` and `council`. Each role's bot file must list the entry's provider. |
| `FOREMAN_EVAL_CASES`                                                           | The case ids to run, separated by commas. Unset or empty: every case.                                                                                                                                                                                                                                                                                            |
| `FOREMAN_EVAL_CAP_USD`                                                         | The weekly cap (D-204).                                                                                                                                                                                                                                                                                                                                          |
| `FOREMAN_EVAL_SPENT_USD`                                                       | What earlier runs of the week spent, from the results table. Unset: 0.                                                                                                                                                                                                                                                                                           |
| `FOREMAN_MODEL_BASE_URLS`                                                      | A JSON object from each provider's name to its address on the job's proxy, `http://<proxy>:<port>/<provider>`, as a run's `base_url_env` names it. The SDK adds `/v1/messages`.                                                                                                                                                                                  |
| `FOREMAN_FLEX_CAPACITY_RETRIES`, `FOREMAN_MAX_OUTPUT_TOKENS`, `FOREMAN_EFFORT` | The loop's settings, read with the Messages API image's names, defaults and checks. Only the first is required, as for a run.                                                                                                                                                                                                                                    |

The output is the shared result line, last on stdout, with one log line per run before it. On success its `status` is `success`, `costUsd` is the job's spend and `structured` is `{evalResult: 1, runId, capUsd, spentBeforeUsd, runs, totals}`. Each entry of `runs`, in the job's order (cases by id, then the plan's entries in order), is `{caseId, caseVersion, role, model, provider, tier, outcome, reason, turns, tokens, costUsd, serviceTierServed, minutes}`, with `providerError: {status, type}` for a provider error only and `facts` for a usable answer only. `outcome` is `correct`, `wrong`, `unusable`, `error` or `skipped`, and `reason` a fixed code of that outcome: a score's code, or one of the run's own (`provider_error`, `endpoint_unreachable`, `max_turns`, `max_usd`, `cap_limit`, `max_minutes`, `output_limit`, `refused`, `unknown_stop`, `run_error`, and `cap_reached` for a skipped run). `totals` is `{spentUsd, runs, skipped, models}`, with one `{model, provider, runs, correct, costUsd}` per plan entry. Everything is bounded: at most 300 runs, at most 5 finding files a run, each a plain path, and the whole line below 1 MiB. No text a model wrote and no provider error message is in it, and the placeholder credential is redacted. A run that fails at the provider ends as `error` and the next run starts. A bad setting, a broken plan, unreadable cases or bot files, a case the builders refuse, or a proxy that never answers stops the job with `status: error` and a fixed `errorText`. The job exits 0 only with a `success` line, as the repo map Job does. The runner checks `structured` with the same `checkEvalResult` the image applies before printing.

**What slice 2b wires**, as `src/adapters/agent-runtime/kubernetes/repo-maps.ts` does for the repo map: the Job, its egress proxy with the providers the plan uses (each from the bot files, with its key's secret path), the NetworkPolicies and the key Secrets; the plan from the model catalog and the D-429 models, with Claude's entries in the baseline week only; the cap and the week's earlier spend from the database; a proxy request ceiling that covers the week (the sum of each planned run's turn limit and Flex capacity retries; past it, the proxy refuses with 403 and each later run ends as `provider_error`) and a Job deadline that covers every run's minute limit; reading the result line from the pod's log with at most `EVAL_RESULT_LOG_BYTES`, then `checkEvalResult`; one results row per run; the flow and its schedule (once a day, so it reads the Job the day after it starts it, "The wiring" below); the daily line; the migration (the results table, the cap setting, and catalog prices for V4.1 Flash and Kimi K2.6); and the image's digest pinned in the agent run settings.

## The wiring (slice 2b, D-433, O-156)

**Its own space and keys (D-433).** The Job runs in its own namespace, `foreman-eval`, never in a project's. Every project's namespace is `agents-<slug>` (`agentNamespace`), so a name that does not start with `agents-` can never be one, whatever slug a project takes; `foreman-` is the prefix of Foreman's own namespaces. It has an agent namespace's objects (Pod Security Admission `restricted`, `default-deny`, a ResourceQuota, and the runner's Role and RoleBinding, the agent namespaces' own, so no new right) and no project label and no run watcher Role, since its Jobs are no runs. It is not in `projects` of the settings file, which the infrastructure stack, the register-project form and the run watcher read: the file has its own `eval` entry with its quota (4 pods, 2 CPUs, 2 GiB of memory, 3 GiB of ephemeral storage, no volume). The runner's client works in the agent namespaces and this one only. The keys are their own Windmill secret variables, `f/foreman/eval/models/deepinfra` and `f/foreman/eval/models/anthropic`, copies of the project keys that Didi makes; the flows' scope `variables:read:f/foreman/*` covers them. The `model_eval` setting names them, and its reader refuses any key path but `eval/models/<provider>`, and the flow's key reader any path outside `eval/models/`, so no setting can send a project's or the platform's secret to a provider. The egress proxy's list of key paths takes `eval/...` beside `platform/...` and `projects/...`. Rejected (D-433): the rehearsal project's namespace and keys.

**The setting** (`model_eval`, migration 0027): the cap, 10 USD a week (D-204); the weekly models, DeepSeek V4 Pro, DeepSeek V4.1 Flash and Kimi K2.6 on DeepInfra at Flex for QA, Triage and the Council; the baseline, Claude Opus 5.5 for QA and Claude Sonnet 5.5 for Triage and the Council on Anthropic at Standard (D-429); its cadence, `first_run_of_month`; and the key paths. Migration 0027 also adds V4.1 Flash and Kimi K2.6 to the model catalog at the prices read on 2026-11-19, with no route to either.

**How a week runs.** Weeks start on Sunday at 00:00 UTC. The flow `f/foreman/weekly_model_test` runs once a day at 07:17 UTC (`flows/weekly-model-test.ts`, `flows/lib/model-eval.ts`):

1. It reads the Job that has not ended, if any, through the port (`src/adapters/agent-runtime/kubernetes/eval-jobs.ts`). A Job still running is left. Once it has ended, its key Secret and its proxy are deleted first; then the result line is read from the pod's log, at most `EVAL_RESULT_LOG_BYTES`, with `parseAgentResult`, checked (`src/core/model-eval-result.ts`, the image's contract written again in the core, held to the image's own check by `test/model-eval-contract.test.ts`, since the core cannot import the image's code) and checked against the Job (its id, cap, spend so far and plan). Then one row per run and the Job's end are stored in one transaction, and only then are the Job's objects deleted, so a failed write reads the Job again the next day. A Job that failed is ended with a fixed reason (`start_failed`, `deadline`, `did_not_end`, `job_gone`, `job_failed`, `bad_result`) and, for `job_failed`, the Job's error text in plain words. A Job still running 30 minutes past its deadline is stopped.
2. On the first run of a week whose Jobs have not run, it starts the week's Job (`src/core/model-eval.ts` `planWeekStart`): never under the kill switch or in dry run, never while `runSettings.evalImage` is empty, and never while another Job is open. The plan takes each model's price from the catalog at its tier, as a run records it; a model without a usable price is left out and named. Claude's baseline is in the first Job of each calendar month (UTC) whose Claude runs started: a month whose first Job ran none of them (the cap reached first, or the Job lost) tries again the next week. The spend so far is what the week's earlier Jobs spent; a Job that ended without a readable result after it may have run leaves it unknown, and then the week starts nothing more, since its cap counts as spent. The flow reads the keys of only the providers the plan uses (the Anthropic key only in the baseline week), writes the Job's row, then creates the key Secret, the two NetworkPolicies, the proxy with the plan's providers (each the bot files' entry for it, with its eval key path; no CONNECT host and no state API) and the Job, and returns. The keys go only into the Secret the proxy reads.
3. The sizes cover the week: the proxy's request ceiling is the sum of each planned run's turn limit and Flex retries (at most 10,000), its 429 allowance each run's `max_rejected_model_requests` (at most 1,000), and the Job's deadline every run's minute limit plus 10 minutes for its start, refused past one day. A week with the baseline plans 48 runs, about 2,300 requests and a deadline of 970 minutes. The flow names the cases the Job runs (`FOREMAN_EVAL_CASES`), from its own copy of `eval/cases/` in its bundle, so the Job runs what was sized; a Job whose image lacks a case refuses before any model call. A finished Job is kept three days, so the next day's run still finds it and its log.

Why the flow never waits for the Job, as the repo map's read does: Windmill counts one execution per second of a job's run (D-369), and a week's Job runs for an hour or more, so a waiting flow would spend thousands of the 10,000 a month, and Windmill's own time limit for a job may stop it first. Reading it the next day costs a second or two; the flow's 30 daily runs a month cost about as much as the scan's.

**The daily line.** The daily check shows the latest week with results under "Weekly model test" (`src/core/model-eval-summary.ts`): "Week of 2026-11-22 (weeks start on Sunday, UTC), with the Claude baseline: 47 runs, 1 skipped at the cap, $2.31 of the $10.00 cap.", then per model "deepseek-ai/DeepSeek-V4-Pro-0813 (deepinfra): 11 of 12 correct, $0.12.", then "Since the week of 2026-11-15: newly wrong: ...; newly right: ..." (or "No case changed since the week of ...", or "No earlier week to compare with."), and "Every tested model got these right 8 weeks in a row, so each is a candidate for a harder case (D-428): ..." when a case has, at one version, in the last 8 weeks with results. A Job still running and the newest Job when it failed are said too. Before the first Job: "No weekly model test yet."

## What it does not do

- It never touches a real repository, never creates a work item, never writes a `runs` row and never merges. ADR 0114 section 7 had the set's results in the scorecard under a `:eval` task type suffix. D-430 puts them in their own table instead, so the set never feeds the scorecard or a routing proposal by itself. Results inform Didi; a routing change stays a migration Didi approves.
- No Developer cases in v1, and so no runtime comparison yet (D-206 expected the set to compare runtimes; QA, Triage and the Council have one runtime). No visual cases: `qa:visual` and `council:visual` have their own model test (D-249).
- No model judges another model's answer. Every score comes from the runner's checks and a fixed rule per role.
- No real personal data and no real secret in any case.

## How the set matures

A case changes only by a pull request Didi merges. Editing a case's input, tree or expectation raises its version, so results are compared only within one version. A new case records where it came from: the item and the run that missed, or the decision that corrected a bot. Once the first real project has merged work, its items replace the tiny-helper cases, one pull request each. The 8-week flag in the daily line proposes which case to replace next; Didi decides.

## Constraints

- Spending stays inside D-204's cap of 10 USD a week, enforced before each run, Claude's baseline included.
- Open models run on DeepInfra Flex only (D-204, D-207).
- Agents never hold a model key (ADR 0106 section 5). The weekly run reaches the providers through an egress proxy that adds the key, as agent runs do.
- No case holds a real secret or personal data. A planted key is fake, says so, and passes the secret scanners.
- The harness never carries its own copy of a rule: instructions, schemas and checks are the runner's, read where the runner reads them.

## How success is judged

- `npm run check` loads every case, builds every case's input with the runner's builders, and shows that each case's example answer passes the runner's check and scores correct, and that wrong answers score wrong. (This slice.)
- Each week the daily check names, per model, the cases it got right and the week's cost, and the week stays under the cap.
- Within a month the set shows a difference between models that live runs did not: a QA model that passes a planted defect, or a Triage model that splits a one-helper plan.

## Consequences

- A model change for QA, Triage or the Council can point to the set's results, not only to live runs.
- Changing a bot file's instructions or a runner check changes the set's runs with it, since the set reads both from where the runner does. A change that makes a model worse shows in the next weekly line.
- The cases need care: each new role or task type, and each real miss, adds a case through review.
- `eval/` is a new folder at the repository root. The README's layout table does not list it yet.
- The test job's image holds the cases, so a changed case needs a new image: the Images workflow builds on a change under `eval/`. The build context keeps the case trees' own test files (`.dockerignore`), which the loader checks byte for byte.

## Open points

- **Where the weekly run executes.** Decided by D-432: as a Kubernetes Job behind the egress proxy, like the repo map Job and the agent runs. The proxy adds the model key to each request, so no Foreman code holds a key, and every model call keeps the proxy's request ceiling, 429 counting and served-tier reading (D-423). Rejected: a Windmill script holding the key and calling DeepInfra directly, which would widen the flow import boundary (ADR 0101, build plan M3.1) and be the first model call outside the proxy. Slice 2a builds the Job's image; slice 2b starts it.
- **QA's missing diff.** Fixed by D-431 (O-154): QA's real input now carries the changed files and the diff at the head commit, and the set's QA inputs carry them through the same builder. The rest of ADR 0112's default context (the files the changed files import, related tests, the spec and ADRs) QA still reaches through its read-only tools.
- **Recorded texts.** The work items of the QA cases are written for the set from the pull requests and the plans, since the items Triage made are in Foreman's database and were not read. The truncate plan was given with its middle part left out, and the case uses it that way. A later version of those cases should use the texts exactly as Foreman recorded them.
- **One run per case.** Whether one run per model and case is steady enough to compare models week to week, or each case needs three runs as the vision model test uses.
