# M0.3 spike: Linear API (V-02)

- **Question:** can Linear's API create and rename statuses, and can an app create issues and comments under its own identity?
- **Status:** desk result, 2026-10-28. **Not run yet. Moved to the start of Milestone 5 (D-147)**, so it is not needed to finish Milestone 0. The run needs a test Linear team and an OAuth app installed in it. Both are gates for Didi.
- **Script:** [`spikes/m0.3-linear-api/linear.ts`](../../spikes/m0.3-linear-api/linear.ts). It refuses to run against team key `DIDI`.

## Desk results

Sources: Linear's public GraphQL schema (`github.com/linear/linear`, `packages/sdk/src/schema.graphql`), Linear's official demo app `linear/weather-bot`, and search summaries of linear.app developer pages. linear.app itself could not be opened from this cloud session.

| Capability                 | Provisional answer        | Evidence                                                                                                                                                                                                                     |
| -------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create an issue as the app | **Likely yes**            | `issueCreate` exists. An OAuth app installed with `actor=app` writes as itself: `Issue.botActor` is set and `Issue.creator` is null. Linear's own demo app does this with scope `read,write,app:assignable,app:mentionable`. |
| Comment as the app         | **Likely yes**            | `commentCreate`, same `actor=app` mechanism.                                                                                                                                                                                 |
| Rename a status            | **Likely yes**            | `workflowStateUpdate` can change `name`, `color`, `description` and `position`. A status's `type` cannot change after it is created.                                                                                         |
| Retire a status            | **Yes, with a condition** | `workflowStateArchive` works only when every issue in that status is archived. There is no delete.                                                                                                                           |
| Create a status as the app | **Unclear, probably no**  | `workflowStateCreate` exists, but similar settings changes need the `admin` scope, and Linear's docs say an `actor=app` app cannot also ask for `admin`.                                                                     |

Rate limits are far above what a 5-minute mirror needs (5,000 requests an hour for an OAuth app). An installed app is not a billable user, per Linear's docs.

## Fallback for creating statuses

If the app cannot create statuses, the one-time status setup (M5.1) runs once with an admin's token, or by hand from a runbook. After that the app only reads statuses and moves issues between them, which needs `write`, not `admin`. This fits M5.1 already: "a script if M0.3 showed the API can do it, otherwise a manual runbook."

## What the run needs (gates for Didi)

- A test Linear team. Not Didi Build.
- An OAuth app registered in Linear, installed in that workspace with `actor=app` and scope `read,write`. A workspace admin approves the install.
- Settings: `LINEAR_TOKEN` (the app's token), `LINEAR_TEST_TEAM_KEY`, `LINEAR_EXPECTED_WORKSPACE` (the workspace's url key; the script refuses any other workspace). Whether to use a separate workspace is N-21.
