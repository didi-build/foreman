# Guards

The guards from ADR 0105's guard list: 24 built in M2.2, `no_merge_conflict_on_head` and `qa_rounds_below_cap` added for the merge guard in M3.3 (D-218), and `no_failed_qa_verdict_on_head` added in M3.5 (O-42). Code: `src/core/guards/`, one pure function per guard, registered in `src/core/guards/index.ts` as `GUARDS`. Tests: next to each file, plus `test/guards-registry.test.ts` (the registry against the ADR) and `test/guards-walkthrough.test.ts` (a code item to Done with the real guards).

## Rules every guard follows

- A guard reads only its `GuardContext`: the node and read-only store calls (`getNode`, `listEdges`, `listEvidence`, `listTransitions`, `getDecision`, `getCounter`, `getSetting`, `getRun`, `listRuns`, `findOpenGateRequest`, `listOpenGateRequests`, `listDecisionsForNode`, `getProject`). M2.2 added the last four. It has no write call.
- A guard never throws on bad data. A malformed payload makes the guard fail with a detail that names the evidence kind.
- A guard never calls a model. `scope_matches_plan` fails with "needs Council" when the spec goes beyond the plan (D-177).
- Each guard returns `{guard, pass, evidenceIds, detail}`. The evidence ids name what it relied on.

## The head commit

A guard that reads "on the current head commit" takes the head from the most recent `ci_run` evidence on the node (latest `recordedAt`, then id). GitHub ingestion (M2.3) records a `ci_run` for every new head commit as soon as its checks start, with conclusion `pending`, so the latest `ci_run` names the head. Evidence for any other commit is stale and ignored. No `ci_run` means no linked PR yet, and every head-commit guard fails.

GitHub ingestion (`src/core/github-ingest.ts`, ADR 0113) keeps this true. It records a `ci_run` only when the commit is the PR's head as GitHub reports it at that moment, so a late event about an older commit records nothing. It skips a `pending` row when the commit already has a `ci_run`, so a late or repeated `pending` never hides a finished result. A check rerun that changes the result on the head records a new row, which becomes the newest.

Head-scoped guards: `ci_green_on_head`, `docs_updated_or_none`, `qa_verdict_independent_on_head`, `privileged_paths_approved`, `no_merge_conflict_on_head`, `spec_components_exist`, `no_failed_qa_verdict_on_head`.

A `docs_note` written by an agent through the state API carries no commit. It counts for the head when it names the head commit, or when it has no commit and was recorded at or after the head's `ci_run`.

## The merge guard (M3.3, D-218)

Every move on which the runner merges a PR (In QA review to Verifying on staging, on every track) carries the same checks: `qa_verdict_independent_on_head`, `docs_updated_or_none`, `ci_green_on_head`, `no_merge_conflict_on_head`, `qa_rounds_below_cap`, `privileged_paths_approved` and `prod_env_protected` (on the design track too, D-224). `test/contracts-consistency.test.ts` holds both files to this set.

`no_merge_conflict_on_head` reads the newest `merge_check` on the head commit. The runner records it itself, right before it merges (`src/core/merge.ts`): it reads the PR's `mergeable` from GitHub for the head GitHub reports, and records nothing when that head is not the node's head. The guard passes only on `true`. `false` (a conflict), `null` (GitHub has not worked it out yet) and a check for any other commit fail. A base branch that moves after the check is caught by GitHub, which refuses a merge it cannot make, and by the fresh check on the next attempt.

`qa_rounds_below_cap` passes while `qa_round < qa_round_cap`. The merge counts no round, so nothing is added to the count, unlike `not_third_failed_round` on the fail move, which runs before its own round is counted.

QA's fail move adds one to `qa_round` and to `failure` in the same transaction, then asks for the escalation, which `escalation_trigger_met` allows once `failure` reaches `failure_threshold` (P-03, D-169, O-41). The round that reaches the cap is refused by `not_third_failed_round`; `escalation_trigger_met` then passes on QA's failed verdict on the head, recorded in the current state, for that round (`qa_round + 1 >= qa_round_cap`), and the runner counts the round in the escalation's own transaction. So with the cap at 3, two failed rounds send the item back with `qa_round` at 2, a pass after them still merges (`2 < 3`), and the third failed verdict goes to Escalated to Council with `qa_round` at 3. All of these moves take the run's trigger id, so a repeated report counts once.

## Into In QA review on a new head only (M3.5, O-42)

Every move into In QA review from a building state (In development, Building components) carries `no_failed_qa_verdict_on_head`: QA has not failed the head commit. After QA fails a head, a done report on the same head is refused, so QA never runs again on code it already failed. A new commit is a new head, and the old verdict is stale for it.

## Failure counts with no move (M3.5, P-03, O-43, O-44)

Two P-03 counts have no move of their own, so the runner records each as `failure_count` evidence in the transaction that adds one to `failure` (`src/core/failures.ts`), under a key that names its cause and run (`runner:failure_count:<cause>:run-<run id>`). A repeated report or a retried flow finds the key and counts nothing more. After each, the runner asks for the escalation with the same trigger, and `escalation_trigger_met` allows it once `failure` reaches `failure_threshold`.

- `report_refused`: a Developer's or Designer's done report whose every move the guards refused (`src/core/run-reports.ts`). Not counted: CI still `pending` on the head, a refusal by `scope_matches_plan` alone, and any QA report. The builder's next run is then due (cause `refused`).
- `dispatch_failed`: a run the runner admitted and ended `fail` because its task or its start failed (no handle), when the run before it on the item failed to start too. A refusal that admits no run never counts.

Dry run and the kill switch count nothing.

## Out of the escalation (M3.5, O-46)

`src/core/escalations.ts` takes an escalated item on. In Escalated to Council: when `council_decision_recorded` passes, the item returns to the state it was escalated from with both counters reset in the same transaction (trigger `council_decision:<decision id>`); otherwise the runner opens the question for Didi and moves the item to Escalated to Didi (same trigger). In Escalated to Didi: when `didi_answer_recorded` passes, the item returns with both counters reset (trigger `didi_answer:<decision id>`). Each runs in the reconcile flow's live pass, and the approval resume step runs it right after an answer to an escalation question.

## The merge commit

`staging_check_on_merge_commit` and `staging_check_failed` read the most recent `merge_commit` evidence. Its `commitSha` is the merge commit on main, and every staging fact they read is recorded on that commit. The staging check counts only when staging served the merge commit, or a later commit on main that GitHub's compare showed contains it (D-225, O-38, O-39). The head commit does not count.

## Staging verification (M3.4)

The runner records what the staging guards read itself (`src/core/staging.ts`, essential 6). No agent writes a staging kind.

- `staging_deploy`: GitHub reports a `staging` deployment whose latest status is `success`, of the merge commit or of a later commit on main that contains it (O-34, D-225). The runner reads GitHub's deployments of the merge commit and its latest 20 `staging` deployments of any commit, and the newest finished one whose commit counts decides (O-38). The merge commit itself counts. A later commit counts when GitHub's compare shows it is `ahead` of the merge commit and main's head is `identical` to or `ahead` of it (it is on main; the branch is `main` for every project), and its row records `onMain: true` and `mainHeadSha`. A deploy of the head, of a commit `behind` or `diverged` from the merge commit, or of a branch that is not on main, records nothing. It is a fact, recorded in dry run too, under the key `github:staging_deploy:<repo>:deployment-<id>` for a deploy of the merge commit and `github:staging_deploy:<repo>:deployment-<id>:covers-<sha>` for a later one, which may cover several items. The check runs only once one exists.
- `staging_deploy_failed`: the newest finished covering deployment has latest status `failure` or `error` (D-225). Recorded like `staging_deploy`, under `github:staging_deploy_failed:<repo>:deployment-<id>:covers-<sha>`, and it takes the fail path below with no check run.
- `staging_check`: the runner's own smoke check of staging (ADR 0107), run in live mode only. It counts only when staging reports it serves the merge commit or a commit on main that contains it, and is recorded on the merge commit once per merge commit under the key `runner:staging_check:<repo>@<sha>` (O-35), with the served commit and its containment (O-39).
- `staging_no_result`: a check that could not reach staging, ran out of time, or found staging serving a commit that does not contain the merge commit or is not on main. Keyed `runner:staging_no_result:<repo>@<sha>:<state since>:<attempt>`. The first is re-dispatched on the next call; the second sends the item to the Council (O-36).

A passed check takes the move to Done, which resets `failure` and `qa_round` in the same transaction, then asks for the release of every item the Done item blocks (trigger `done:<node id>`; `blockers_done` and `design_spec_merged` decide). A failed check takes the fallback move back to In development or Building components, which adds one to `failure` in the same transaction, then asks for the escalation, which `escalation_trigger_met` allows once `failure` reaches `failure_threshold` (O-37). A failed staging deploy takes the same fail path. The moves have the trigger `staging_check:<evidence id>`, or `staging_deploy_failed:<evidence id>` for a failed deploy, so a repeated call writes one row and counts once.

An item in Verifying on staging with no `staging_deploy` or `staging_deploy_failed` recorded for longer than `staging_deploy_attention_after_minutes` (60) goes on the reconcile report's attention list as a `staging_deploy_wait` item (D-225, O-40). It changes no guard.

The runner's merge writes `merge_commit` under the same ingest key as GitHub ingestion, with `recordedBy` `runner`, so the merge is recorded once whichever writes first. `merge_check` rows have `recordedBy` `runner` and a `ref` of `github:merge_check:<repo>#<pr>:<sha>`; there is one per attempt and the newest counts.

`ci_run` and `merge_commit` rows written by GitHub ingestion have `recordedBy` `github`, no run, and a `ref` equal to their ingest key (`github:ci_run:<repo>#<pr>:<sha>:pending`; a final result adds its CI attempt, `github:ci_run:<repo>#<pr>:<sha>:<conclusion>:check-run-<id>` with the highest counted check run id, so every rerun is a new row; `github:merge_commit:<repo>#<pr>`). Ingestion always fills `changedPaths`.

## Topic keys and decision conventions

- Visual approval topic: `visual-approval:<nodeId>`. Escalation topic: `escalation:<nodeId>`. Reversal topic: `decision-reversed:<decisionId>`.
- A node's decisions are the ones recorded on it plus the ones linked through `node_decisions`. Only `active` decisions count.
- `plan_attached`: an active `product_direction`, and an active `council_decision` with `scope.kind` `plan_accepted`.
- `privileged_paths_approved`: an active `approval` by `didi` with `scope {kind: "privileged_path", commitSha: <head>}`. A new commit needs a fresh approval. The merge opens a `privileged_path` gate request owned by `didi` on the topic `privileged-path:<nodeId>`, with payload `{commitSha, repo, pr, paths}`, and the approval page's answer copies `kind` and `commitSha` from it into the decision's scope (`src/core/approvals.ts`). A request for a newer head supersedes the older one.
- `approval_recorded`: the latest active decision on the visual topic is an `approval` by `didi` with non-empty verbatim text.
- `changes_requested_recorded`: an active `answer` by `didi` on the visual topic with `scope.outcome` `changes_requested` or `rejected`.
- `scope_matches_plan`: passes when the latest `spec_paths` declares nothing beyond the plan, or when an active `council_decision` with `scope.kind` `scope_approved` was recorded after that spec.
- `council_decision_recorded`: an active `council_decision` since the node entered its state, with `scope.changesProductDirection === false` and `scope.passesGate === false`, and `scope.outcome` not `cannot_resolve` (the Council's way to say it cannot resolve the item, M3.5). Anything else goes to Didi (D-177).
- The question for Didi: one open `escalation` gate request owned by `didi` on the escalation topic, with payload `{question, councilDecisionId, councilNote, returnState}`, opened by the runner in live mode (M3.5). The approval page's answer carries the topic key in its scope, which `didi_answer_recorded` reads.
- A reversed decision: a `decision_events` row, every node linked to it through `node_decisions` marked `stale`, and one open `council_question` gate request owned by the Council on the reversal topic, with payload `{decisionId, reason, staleNodeIds}`, in one transaction. A repeat writes nothing again (ADR 0104, O-45).
- `didi_answer_recorded`: an active decision by `didi` on the escalation topic since the node entered its state, with non-empty verbatim text.

## Settings and project fields read

- `failure_threshold` and `qa_round_cap` (settings) against the `failure` and `qa_round` counters.
- `designer_identity` (setting): the only author allowed on spec commits.
- `project.privilegedPathsExtra` adds to the default privileged paths: `**/migrations/**`, `.github/**`, `docs/privacy/**`, `**/*secret*`, `**/*secret*/**`, `**/.env*`.
- `project.prodRequiresApproval` for `prod_env_protected`.
