# Guards

The guards from ADR 0105's guard list: 24 built in M2.2, `no_merge_conflict_on_head` and `qa_rounds_below_cap` added for the merge guard in M3.3 (D-218), `no_failed_qa_verdict_on_head` added in M3.5 (O-42), `council_redo_recorded` added by D-231, and `unpicked_options_removed` added for the design track's merge by D-258. Code: `src/core/guards/`, one pure function per guard, registered in `src/core/guards/index.ts` as `GUARDS`. Tests: next to each file, plus `test/guards-registry.test.ts` (the registry against the ADR) and `test/guards-walkthrough.test.ts` (a code item to Done with the real guards).

## Rules every guard follows

- A guard reads only its `GuardContext`: the node and read-only store calls (`getNode`, `listEdges`, `listEvidence`, `listTransitions`, `getDecision`, `getCounter`, `getSetting`, `getRun`, `listRuns`, `findOpenGateRequest`, `listOpenGateRequests`, `listDecisionsForNode`, `getProject`). M2.2 added the last four. It has no write call.
- A guard never throws on bad data. A malformed payload makes the guard fail with a detail that names the evidence kind.
- A guard never calls a model. `scope_matches_plan` fails with "needs Council" when the spec goes beyond the plan (D-177).
- Each guard returns `{guard, pass, evidenceIds, detail}`. The evidence ids name what it relied on.

## The head commit

A guard that reads "on the current head commit" takes the head from the most recent `ci_run` evidence on the node (latest `recordedAt`, then id). GitHub ingestion (M2.3) records a `ci_run` for every new head commit as soon as its checks start, with conclusion `pending`, so the latest `ci_run` names the head. Evidence for any other commit is stale and ignored. No `ci_run` means no linked PR yet, and every head-commit guard fails.

GitHub ingestion (`src/core/github-ingest.ts`, ADR 0113) keeps this true. It records a `ci_run` only when the commit is the PR's head as GitHub reports it at that moment, so a late event about an older commit records nothing. It skips a `pending` row when the commit already has a `ci_run`, so a late or repeated `pending` never hides a finished result. A check rerun that changes the result on the head records a new row, which becomes the newest.

Head-scoped guards: `ci_green_on_head`, `docs_updated_or_none`, `qa_verdict_independent_on_head`, `privileged_paths_approved`, `no_merge_conflict_on_head`, `spec_components_exist`, `no_failed_qa_verdict_on_head`, `unpicked_options_removed`.

A `docs_note` written by an agent through the state API carries no commit, unless it names one: since D-236 the state API stores a full 40-character sha the agent sends on a `docs_note`, and on no other kind. The OpenCode wrapper sends the PR's head as it read it from GitHub. A note counts for the head when it names the head commit, or when it has no commit and was recorded at or after the head's latest `ci_run`. A note naming an older commit never counts once the head has moved.

## The merge guard (M3.3, D-218)

Every move on which the runner merges a PR (In QA review to Verifying on staging, on every track) carries the same checks: `qa_verdict_independent_on_head`, `docs_updated_or_none`, `ci_green_on_head`, `no_merge_conflict_on_head`, `qa_rounds_below_cap`, `privileged_paths_approved` and `prod_env_protected` (on the design track too, D-224). The design track's merge also carries `unpicked_options_removed` (D-258). `test/contracts-consistency.test.ts` holds the code track's merge to exactly this set and the design track's to this set plus `unpicked_options_removed`.

`unpicked_options_removed` (`src/core/guards/options.ts`) checks that the PR no longer carries the folder of an exploration option Didi did not approve (D-253). It reads the head `ci_run`'s `changedPaths`, as `privileged_paths_approved` does, and takes each path's option folder: `design/<area>/<feature>/options/<name>`, any folder named `options` under `design/` with a folder before it, whatever the name. The approved option's folder is the `path` of the runner's `screenshot` of the option that Didi's latest active approval on the visual-approval topic names (`approvedOptionRecord`, `src/core/visual-comparison.ts`). It passes when the PR has no option folder, or only that one. It fails naming every other option folder (paths only, at most 20, the rest counted), including one of another feature or one no request listed. It fails closed when `changedPaths` is not recorded on the head, and when option folders are present but no approved option's folder is recorded. It is a contract guard only on the design track, since only design items have exploration options, so the code track's merge is unchanged (O-69). When it fails because option folders Didi did not approve are still in the PR, QA's report takes QA's fail move (D-259, below). When it fails closed for missing data, the refused merge takes the move's fallback: the item stays In QA review with the guard named, since there is nothing for the Designer to fix.

Leftover option folders are a QA fail (D-259, settles N-60, O-70). On the design track `qa_failed_with_findings` also passes when a QA run on the head ended `success` and the PR at that head still carries option folders Didi did not approve, the case in which `unpicked_options_removed` names them (`unpickedOptionsLeft`, beside `failedVisualComparison` in `src/core/guards/review.ts`). It does not pass when the folder check fails closed: no `ci_run`, a malformed one, no `changedPaths`, or option folders with no approved option's folder recorded. QA's report asks for the merge first, in contract order; once the merge is refused, the same report asks for QA's fail move with the run's trigger, so the item goes back to Building components with the head `ci_run` as the move's evidence, counted as a failed QA round and a failure (P-03), once for a repeated report. The round that reaches the cap goes to the Council: `escalation_trigger_met` reads such a report in the current state as that round. The Designer's input says why the item came back (`unpicked_options_left`): each leftover folder, paths only, sorted, at most 20 with the rest counted, with the instruction to delete them and keep the approved option's folder. `no_failed_qa_verdict_on_head` refuses a done report on that same head while the folders remain, so the Designer pushes a new commit. The code track is unchanged.

`no_merge_conflict_on_head` reads the newest `merge_check` on the head commit. The runner records it itself, right before it merges (`src/core/merge.ts`): it reads the PR's `mergeable` from GitHub for the head GitHub reports, and records nothing when that head is not the node's head. The guard passes only on `true`. `false` (a conflict), `null` (GitHub has not worked it out yet) and a check for any other commit fail. A base branch that moves after the check is caught by GitHub, which refuses a merge it cannot make, and by the fresh check on the next attempt.

`qa_rounds_below_cap` passes while `qa_round < qa_round_cap`. The merge counts no round, so nothing is added to the count, unlike `not_third_failed_round` on the fail move, which runs before its own round is counted.

QA's fail move adds one to `qa_round` and to `failure` in the same transaction, then asks for the escalation, which `escalation_trigger_met` allows once `failure` reaches `failure_threshold` (P-03, D-169, O-41). The round that reaches the cap is refused by `not_third_failed_round`; `escalation_trigger_met` then passes on QA's failed verdict on the head, recorded in the current state, for that round (`qa_round + 1 >= qa_round_cap`), and the runner counts the round in the escalation's own transaction. So with the cap at 3, two failed rounds send the item back with `qa_round` at 2, a pass after them still merges (`2 < 3`), and the third failed verdict goes to Escalated to Council with `qa_round` at 3. All of these moves take the run's trigger id, so a repeated report counts once.

## Into In QA review on a new head only (M3.5, O-42)

Every move into In QA review from a building state (In development, Building components) carries `no_failed_qa_verdict_on_head`: QA has not failed the head commit. After QA fails a head, a done report on the same head is refused, so QA never runs again on code it already failed. A new commit is a new head, and the old verdict is stale for it.

## Failure counts with no move (M3.5, P-03, O-43, O-44)

Two P-03 counts have no move of their own, so the runner records each as `failure_count` evidence in the transaction that adds one to `failure` (`src/core/failures.ts`), under a key that names its cause and run (`runner:failure_count:<cause>:run-<run id>`). A repeated report or a retried flow finds the key and counts nothing more. After each, the runner asks for the escalation with the same trigger, and `escalation_trigger_met` allows it once `failure` reaches `failure_threshold`.

- `report_refused`: a Developer's or Designer's done report whose every move the guards refused (`src/core/run-reports.ts`). Not counted: CI still `pending` on the head, a refusal by `scope_matches_plan` alone, and any QA report. The builder's next run is then due (cause `refused`).
- `dispatch_failed`: a run the runner admitted and ended `fail` because its task or its start failed (no handle), when the run before it on the item failed to start too. A refusal that admits no run never counts.

Dry run and the kill switch count nothing.

## Out of the escalation (M3.5, O-46)

`src/core/escalations.ts` takes an escalated item on. In Escalated to Council: when `council_decision_recorded` passes, the item returns to the state it was escalated from with both counters reset in the same transaction (trigger `council_decision:<decision id>`); otherwise the runner opens the question for Didi and moves the item to Escalated to Didi (same trigger). In Escalated to Didi: when `didi_answer_recorded` passes, the item returns with both counters reset (trigger `didi_answer:<decision id>`). Each runs in the reconcile flow's live pass, and the approval resume step runs it right after an answer to an escalation question. Both moves back are `runner_only` (O-54): only this pass takes them, so no other path returns an item without the reset.

## The Council's run and its answer (D-228, D-229)

`src/core/council.ts` with `flows/lib/council-runs.ts`. An item in Escalated to Council with no Council decision, and a reversal's open Council question, each get one Council run through the dispatch (task type `council`); the run carries its question's topic (`runs.question_topic`, migration 0014). The Council has no tools. When its run ends, the runner checks the structured answer against the schema of its question's kind and records the `council_decision` itself, once per run, before it records the run's end; the Council never writes a decision or evidence a guard reads. An answer that fails the schema ends the run `fail`. After two unusable runs the question goes to Didi (O-47 to O-50). A reversal answer's `redo` is taken by the redo move below, or by a rework item for a merged item.

When Didi answers a reversal's gate request (the `escalation` request owned by `didi` on its `decision-reversed:` topic), the reversal gets one follow-up Council question (D-234, O-56): an open `council_question` owned by the Council on the same topic, with payload `{decisionId, reason, staleNodeIds, didiDecisionId, didiGateRequestId}`, for the items of Didi's request that are still stale. Its run's input quotes Didi's choice and words as data. Its answer is recorded and applied as any reversal answer; a `cannot_decide`, or no usable answer after its one re-run, sends those items back to Didi with one new gate request, and only a new answer from Didi opens another follow-up. The approval resume step opens it and starts its run; the reconcile flow's follow-up pass opens any that is still due. Live mode only: under the kill switch or in dry run Didi's answer is recorded and nothing acts on it (D-201).

## Back to the start on a Council redo (D-231, O-51 to O-53)

`council_redo_recorded` (`src/core/guards/council.ts`) guards every move that sends a stale item back to the start of its track: In development and In QA review to Ready for dev, and In design exploration, Waiting for Didi, Writing spec, Building components and In QA review to Ready for design exploration. No move leaves Verifying on staging or Done this way, since every item there is merged.

The runner links each item a reversal answer gives a verdict for to that answer (`node_decisions`), and the answer's scope names the items whose flags it cleared (`clearedNodeIds`). The guard reads the item's own decisions and transitions:

- The item's stale episode starts after its last way out of stale: an answer that cleared its flag, an applied redo move (trigger `council_redo:<Council decision id>`), or a rework item opened for it (a `reworks` edge to it, D-233).
- Every decision about the item reversed in that episode needs a Council answer for the item, recorded after the reversal, that is not `cannot_decide`. When one reversal has more than one Council answer (a follow-up after Didi's answer, D-234), the latest one that gives the item a verdict counts. An open question, or one with Didi, fails the guard.
- The latest active answer in the episode that gives the item `redo` stands. A redo given while another reversal was open is kept: once that one is answered `still_valid`, the redo stands.
- The item is stale and has no `merge_commit`. A merged item's code is on main, so it fails here and gets a rework item instead (D-233).

`src/core/council.ts` takes the move (`redo`), and `flows/lib/council-runs.ts` runs it (`redoPass`) right after a reversal answer and in the reconcile flow's live passes. The pass first cancels every active run on the item but a Council run through the runtime, as the kill switch's cancel pass does (D-202). The move's transaction reads the redo again, refuses with `run_active` while such a run is active, clears the stale flag, resets `failure` and `qa_round`, and cancels the item's open visual-approval request. The item keeps its branch and PR (D-220); the dispatch then starts it as a fresh item. A Developer's or QA's report never takes a redo move, and the moves are `runner_only` (O-54): the library rejects any request for one but `council.redo`'s, including the transition flow's, with `runner_only_move`. Dry run and the kill switch cancel nothing and write nothing.

`approval_recorded` and `changes_requested_recorded` read only an answer recorded since the item entered its state, so an answer about options a redo threw away never moves the item later (O-52).

## A rework item for a merged redo (D-233, O-55)

A merged item (it has a `merge_commit`) whose redo stands is not moved: its code is on main. The redo pass opens one new work item instead (`council.redo`, `src/core/council.ts`): in its track's start state (the target of its track's redo moves: Ready for dev, or Ready for design exploration on the design track), same project and track, titled `Rework: <original title>`, with the Council's notes quoted as data and the reversed decision's id in its `body.description`, and `body.rework {originalNodeId, councilDecisionId, reversedDecisionId, councilNote}`. It is agent-ready and off hold only if the original was. A `reworks` edge links it to the original (from the rework item, migration 0015), and the original's stale flag is cleared, in the same transaction, which locks only the original and opens the item once per Council decision. The rework item then goes through the dispatch, QA and the merge guard like any other item. Dry run and the kill switch write nothing.

## The visual comparison (D-242, D-250, D-252, O-66, O-68)

On the design track `qa_verdict_independent_on_head` needs a passing `visual_comparison` on the head. Only the runner records one, from a QA run of task type `qa:visual` (`src/core/visual-comparison.ts`). The run gets, per component and variant the spec lists, the approved option's crop, the built component's screenshot at the head, the runner's pixel comparison of the two (changed regions and how much changed) and the spec section. It answers `match`, `differs` or `cannot_tell` per pair, with findings. At the run's end the runner checks the answer against `output_schemas.visual` in `contracts/bots/qa.yaml` and its own rules (one entry per pair, no findings on a match, 1 to 10 on the others), and checks that the run's model differs from every Developer and Designer run's model on the item (D-158). Only then does it record `visual_comparison`; an answer it cannot record ends the run `fail` and records nothing.

`pass` is true only when every pair is `match`. Any `differs` records `{pass: false, outcome: "differs"}`; a `cannot_tell` with no `differs` records `{pass: false, outcome: "cannot_tell"}`. Either way the merge guard refuses with "visual comparison failed on head". What happens next (D-252, O-68):

- `differs`: QA's fail move takes it, like any QA fail. `qa_failed_with_findings` also passes on the design track when the latest `visual_comparison` on the head says `differs` with at least one finding, so the visual run's report sends the item back to Building components with the comparison as the move's evidence, counted as a failed QA round and a failure (P-03), and the third such round goes to the Council through `escalation_trigger_met`. The Designer's input then says why the item came back and quotes each component's findings line by line as data (`visual_differs`). `no_failed_qa_verdict_on_head` refuses a done report on that same head, as after a fail verdict.
- `cannot_tell`: the comparison runs once more on the same head. After the first `cannot_tell` in the item's current state, the run-end flow starts one more `qa:visual` run on the head through the dispatch, when no other run on the item is active (`visualRerunCheck`); a review run still at work delays it to that run's end. The report of a visual run that could not tell asks for the escalation; `escalation_trigger_met` passes on the second `cannot_tell` on the head in the current state, so the item goes to Escalated to Council with the blocked reason "the visual comparison could not tell twice on the same head". It is not a failed round.

A new head needs a new comparison: evidence on another commit is stale.

The approved option is the `option` on Didi's latest active approval of the item's visual-approval request (`scope.option`, recorded only when the request's payload lists that name, `src/core/approvals.ts`), and its `screenshot` evidence gives the capture commit, the file and its SHA-256. A file read again with another hash, a missing bundle, a component the gallery bundle did not capture, or more than 20 pairs refuses the run's start.

## The merge commit

`staging_check_on_merge_commit` and `staging_check_failed` read the most recent `merge_commit` evidence. Its `commitSha` is the merge commit on main, and every staging fact they read is recorded on that commit. The staging check counts only when staging served the merge commit, or a later commit on main that GitHub's compare showed contains it (D-225, O-38, O-39). The head commit does not count.

## Staging verification (M3.4)

The runner records what the staging guards read itself (`src/core/staging.ts`, essential 6). No agent writes a staging kind.

- `staging_deploy`: GitHub reports a `staging` deployment whose latest status is `success`, of the merge commit or of a later commit on main that contains it (O-34, D-225). The runner reads GitHub's deployments of the merge commit and its latest 20 `staging` deployments of any commit, and the newest finished one whose commit counts decides (O-38). The merge commit itself counts. A later commit counts when GitHub's compare shows it is `ahead` of the merge commit and main's head is `identical` to or `ahead` of it (it is on main; the branch is `main` for every project), and its row records `onMain: true` and `mainHeadSha`. A deploy of the head, of a commit `behind` or `diverged` from the merge commit, or of a branch that is not on main, records nothing. It is a fact, recorded in dry run too, under the key `github:staging_deploy:<repo>:deployment-<id>` for a deploy of the merge commit and `github:staging_deploy:<repo>:deployment-<id>:covers-<sha>` for a later one, which may cover several items. The check runs only once one exists.
- `staging_deploy_failed`: the newest finished covering deployment has latest status `failure` or `error` (D-225). Recorded like `staging_deploy`, under `github:staging_deploy_failed:<repo>:deployment-<id>:covers-<sha>`, and it takes the fail path below with no check run.
- `staging_check`: the runner's own smoke check of staging (ADR 0107), run in live mode only. It counts only when staging reports it serves the merge commit or a commit on main that contains it, and is recorded on the merge commit once per merge commit under the key `runner:staging_check:<repo>@<sha>` (O-35), with the served commit and its containment (O-39).
- `staging_no_result`: a check that could not reach staging, ran out of time, or found staging serving a commit that does not contain the merge commit or is not on main. Keyed `runner:staging_no_result:<repo>@<sha>:<state since>:<attempt>`. The first is re-dispatched on the next call; the second sends the item to the Council (O-36).

A passed check takes the move to Done, which resets `failure` and `qa_round` in the same transaction, then asks for the release of every item the Done item blocks (trigger `done:<node id>`; `blockers_done` and `design_spec_merged` decide). A failed check takes the fallback move back to In development or Building components, which adds one to `failure` in the same transaction, then asks for the escalation, which `escalation_trigger_met` allows once `failure` reaches `failure_threshold` (O-37). A failed staging deploy takes the same fail path. The moves have the trigger `staging_check:<evidence id>`, or `staging_deploy_failed:<evidence id>` for a failed deploy, so a repeated call writes one row and counts once.

An item in Verifying on staging with no `staging_deploy` or `staging_deploy_failed` recorded for longer than `staging_deploy_attention_after_minutes` (60) goes on the reconcile report's attention list as a `staging_deploy_wait` item (D-225, O-40). It changes no guard.

## Triage and the handoff (M3.6, D-262, D-264, D-269, O-71 to O-75, O-77)

`src/core/triage.ts` with `flows/lib/triage-runs.ts`. Machine 1's contract (`contracts/machine-1/idea.yaml`) has five moves: the three of the planning chat's plan (below) and these two. Plan accepted to Triage is guarded by `plan_attached`, read on the idea: its product direction and its accepted plan. Triage to Handed off has no guard and is runner only: only the handoff step applies it, in the transaction that creates the work items, and the library refuses it to any other request (`runner_only_move`).

An idea in Triage gets one Triage run (task type `triage`) through the dispatch. Its input is the accepted plan, verbatim, and the repo map brief at the default branch's head, and the run records that commit as its `headSha`. When the run ends, the runner checks the structured answer before it records the end, against the bot file's schema and then the repo map at that commit, in this order: the bounds, a non-empty list, unique keys, every path a file or folder in the map or a new file in a folder in it, every check `npm run <script>` with a script in `package.json`, each code, infra or docs track against its paths (only `infra/` or root `wrangler.json`, `wrangler.jsonc` or `wrangler.toml` files is infra, only `docs/` or README files is docs, anything else is code; design is not checked), `blockedBy` keys in the answer with no item blocked by itself and no cycle, a non-design item blocked by every design item unless the note names the design item's key, and a gate on exactly the needsDidi items. The first problem rejects the whole answer with a fixed code and a reason that names the item and, for a path or a check, the value, quoted and cut at 200 characters.

A rejected answer is recorded once per run as an `agent_report` on the idea by `runner`, ref `runner:triage_rejected:run-<run id>`, payload `{reason, code}`, and the run ends `fail`. No guard reads that row: `escalation_trigger_met` reads only an `agent_report` asking to escalate. Triage runs once more, with the reason in its input. When two Triage runs since the idea entered Triage ended with no handoff (not counting `usage_exhausted` and `cancelled`), the runner records an `agent_report` `{escalate: true, reason}` on the idea, ref `runner:triage_escalated:run-<last run id>`, and asks for the escalation with the trigger `triage_unusable:<last run id>`; the Council's run on `escalation:<idea id>` follows. When the Council's decision returns the idea to Triage, its two runs start over and its input carries the Council's note.

A good answer is handed off in one transaction: the idea's move to Handed off with the run's report trigger (`bot_report`, `run:<run id>`), so a repeated or concurrent run end hands off once; each work item on its track's start state (Ready for design exploration for design; Blocked, with a blocked reason, for an item with `blockedBy`; otherwise Ready for dev) in the idea's project, agent-ready, with the answer's hold flag; the item's accepted plan and product direction linked through `node_decisions`, so `plan_attached` passes on it; a `split_into` edge from the idea; a `blocks` edge from each blocker (the library's cycle check, read through the same transaction) and a `design_for` edge from a design blocker to a non-design item; one open blocking gate request owned by Didi for each needsDidi item, of the answer's gate kind, on `needs-didi:<item id>`, which `no_pending_gate` holds the item's dispatch on; for each held item, one open release request owned by Didi (D-269), described below; and one `triage_track` decision record per item. The idea's version check is the only lock. Dry run and the kill switch write nothing.

A held item's release request (D-269, O-77, `src/core/hold-release.ts`): kind `scope`, not blocking (the attention list, no phone alert), on `hold-release:<item id>`, with payload `{question, title, description, ideaId, note?}` (the fixed question, the item, and Triage's note on why the plan holds it) and no options, so the approval form of D-254 shows Decision and Feedback only. While it is open, `agent_ready_not_on_hold` (and `no_pending_gate`) keep the item from starting. Didi's answer is recorded by the approval resume step as on any request. On Approve the runner, and only the runner, clears the item's `hold` flag: one transaction that reads the kill switch and dry run (either writes nothing), locks only the item, and clears the flag only when the item is still held and the latest request on the topic is answered with Didi's active `approval`. Reject or Request changes records Didi's words (Reject and Request changes need feedback, D-254) and the item stays held; no new request opens. The reconcile flow's hold release pass releases an approved item the approval step could not (a switch held it, or it was cut short). A repeated answer finds the request closed and records nothing; a repeated release finds the item no longer held and writes nothing.

## The planning chat's plan (D-266, D-230, O-78)

`src/core/plans.ts`, `src/api/routes.ts` (`POST /plans`), `flows/lib/approval.ts` and the reconcile flow's plan approval pass. The planning chat's identity can call only `POST /plans` (ADR 0102). A submission names the project by slug and carries a one-line title, the plan, the product direction and Didi's answers (each a question and an answer), every text non-blank and bounded, with no other field. It is recorded in one transaction that only inserts: a new idea in Submitted, or an idea of the project in Submitted or Council planning when `ideaId` is given; a `product_direction` decision and one `interview_answer` decision per answer on the idea, by `planning`; and the submission as an `agent_report` on the idea by `planning`, with no run and no commit, payload `{kind: "plan_submission", title, plan, productDirection, answers, directionDecisionId, answerDecisionIds}`. No guard reads that row but the two below.

The runner's plan approval pass opens one request per submission: kind `scope`, owner `didi`, blocking, on `plan-approval:<idea id>`, payload `{question, title, plan, productDirection, answers, ideaId, submissionId}` and no options, in a transaction that reads the kill switch and dry run (either opens nothing) and locks only the idea. A newer submission supersedes an open request. Didi's answer is recorded by the approval resume step (Approve needs no feedback; Request changes and Reject need it, D-254). Then the runner, and only the runner, takes the move: on Approve, Submitted or Council planning to Plan accepted (`plan_approval_recorded`, runner only, trigger `plan_approved:<answer id>`), whose transaction also records `plan_accepted`: a `council_decision` on the idea with `scope {kind: "plan_accepted", topicKey, gateRequestId, approvalDecisionId, submissionId, recordedBy: "runner"}` and the plan the request showed as its text. Triage then starts (the Triage pass, as M3.6 built). On Reject or Request changes, Submitted to Council planning (`plan_return_recorded`, runner only, trigger `plan_returned:<answer id>`); an idea already in Council planning stays there. An answer to a request for an older plan moves nothing. The reconcile flow's pass takes any move the approval step could not (a switch held it, or it was cut short).

## Topic keys and decision conventions

- Visual approval topic: `visual-approval:<nodeId>`. Escalation topic: `escalation:<nodeId>`. Reversal topic: `decision-reversed:<decisionId>`. A needsDidi work item's gate request from the Triage handoff: `needs-didi:<nodeId>` (M3.6). A held work item's release request from the Triage handoff: `hold-release:<nodeId>` (D-269). The planning chat's plan for Didi's approval: `plan-approval:<ideaId>` (D-266). The Council's call on a visual approval: `visual-call:<nodeId>` (D-270).
- A node's decisions are the ones recorded on it plus the ones linked through `node_decisions`. Only `active` decisions count.
- `plan_attached`: an active `product_direction`, and an active `council_decision` with `scope.kind` `plan_accepted`. It guards a design item's dispatch and an idea's move from Plan accepted to Triage (M3.6); the Triage handoff links both decisions to every item it creates.
- `privileged_paths_approved`: an active `approval` by `didi` with `scope {kind: "privileged_path", commitSha: <head>}`. A new commit needs a fresh approval. The merge opens a `privileged_path` gate request owned by `didi` on the topic `privileged-path:<nodeId>`, with payload `{commitSha, repo, pr, paths}`, and the approval page's answer copies `kind` and `commitSha` from it into the decision's scope (`src/core/approvals.ts`). A request for a newer head supersedes the older one.
- `approval_recorded`: the latest active decision on the visual topic is an `approval` by `didi` with non-empty verbatim text, or one that names the approved option (`scope.option`): the approval page's Approve needs exactly one option and no feedback (D-254).
- The approval page (D-254): one form with Decision (Approve, Request changes or Reject), Options (the request's `payload.options`, any number) and Feedback. The runner checks it after it is sent (`approvalAnswerProblem`, `src/core/approvals.ts`): every option named is one the request lists, none twice; Approve on a request that lists options names exactly one, recorded as `scope.option`; Approve on a question for Didi (kinds `escalation` and `council_question`) needs feedback too (D-257); Request changes and Reject need feedback, and record the options they name as `scope.options` (two or more on Request changes ask for one combined option). An answer that breaks a rule records nothing: a fresh request opens on the same topic with the same kind, owner and payload plus `payload.note`, the one-line reason, and the answered one is superseded. On a visual approval the form also has an optional size field, "this was a small tweak" (Yes or No, D-278), recorded as `scope.smallTweak` when Didi picks one; no guard reads it, only the Council's visual-call pairing (`visualCallPairs`). A request opened before D-254 shows the older form (`answer` of Approve, Reject or Changes requested, `reply`, and `option`), which is read the same way.
- `changes_requested_recorded`: an active `answer` by `didi` on the visual topic with `scope.outcome` `changes_requested` or `rejected`.
- `approval_recorded` and `changes_requested_recorded` ignore the Council's visual call: it is recorded on the topic `visual-call:<nodeId>`, never on the visual topic, so neither guard reads it, and it never answers or changes the visual-approval request (D-270).
- `scope_matches_plan`: passes when the latest `spec_paths` declares nothing beyond the plan, or when an active `council_decision` with `scope.kind` `scope_approved` was recorded after that spec.
- `council_decision_recorded`: an active `council_decision` since the node entered its state, with `scope.changesProductDirection === false` and `scope.passesGate === false`, and `scope.outcome` not `cannot_resolve` (the Council's way to say it cannot resolve the item, M3.5). Anything else goes to Didi (D-177). A decision whose `scope.topicKey` names another question (a reversal's answer recorded on the node) is not read; one with no topic key, or the escalation topic, is (O-49).
- The Council's escalation answer, as the runner records it: a `council_decision` by `council` on the node, with `scope {topicKey: "escalation:<nodeId>", runId, outcome: "resolve" | "cannot_resolve", changesProductDirection, passesGate}` and the Council's note as its text (D-228, O-49).
- The Council's call on a visual approval, as the runner records it (D-263, D-270): a `council_decision` by `council` on the item, with `scope {topicKey: "visual-call:<nodeId>", gateRequestId, call, runId}`, `call` either `small_tweak_council_would_approve` or `needs_didi`, and the Council's reason (1 to 1,000 characters) as its text; once per run and once per request, under a lock on the item, while the request is open. With no usable answer after its run and one re-run it is recorded as dropped: the same scope with `call` `dropped`, the last run's id, and the runner's fixed text. No guard reads it and nothing acts on it; `visualCallPairs` (`src/core/visual-call.ts`) pairs each call with Didi's answer on the same request for D-263's later handoff decision.
- The Council's reversal answer, as the runner records it: a `council_decision` by `council` on the run's node, with `scope {topicKey: "decision-reversed:<decisionId>", runId, reversedDecisionId, verdicts: [{nodeId, verdict, note}]}`, a verdict for every stale node of the reversal. In the same transaction the Council question is answered with it, `still_valid` and an initial-state `redo` clear the stale flag unless another open reversal question names the node, and the `cannot_decide` nodes get one open `escalation` gate request owned by `didi` on the reversal topic, with payload `{question, decisionId, nodeIds, councilDecisionId, councilNote}` (D-229, O-50).
- No usable Council answer after two runs: for an escalation, one open `escalation` gate request owned by `didi` on the escalation topic with payload `{question, reason, lastCouncilRunId, returnState}`, then the move to Escalated to Didi (trigger `council_unanswered:<run id>`); for a reversal, one open `escalation` gate request owned by `didi` on the reversal topic with payload `{question, decisionId, nodeIds, reason, lastCouncilRunId}`, which supersedes the Council's question (O-48).
- The question for Didi: one open `escalation` gate request owned by `didi` on the escalation topic, with payload `{question, councilDecisionId, councilNote, returnState}`, opened by the runner in live mode (M3.5). The approval page's answer carries the topic key in its scope, which `didi_answer_recorded` reads.
- A reversed decision: a `decision_events` row, every node linked to it through `node_decisions` marked `stale`, and one open `council_question` gate request owned by the Council on the reversal topic, with payload `{decisionId, reason, staleNodeIds}`, in one transaction. A repeat writes nothing again (ADR 0104, O-45).
- `didi_answer_recorded`: an active decision by `didi` on the escalation topic since the node entered its state, with non-empty verbatim text.

## Settings and project fields read

- `failure_threshold` and `qa_round_cap` (settings) against the `failure` and `qa_round` counters.
- `designer_identity` (setting): the only author allowed on spec commits.
- `project.privilegedPathsExtra` adds to the default privileged paths: `**/migrations/**`, `.github/**`, `docs/privacy/**`, `**/*secret*`, `**/*secret*/**`, `**/.env*`.
- `project.prodRequiresApproval` for `prod_env_protected`.
